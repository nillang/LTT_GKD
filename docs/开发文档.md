# 小狐（LTT_GKD）开发文档

> 产品名称：小狐（XH）
> 类型：Android 无障碍服务广告自动跳过应用
> 技术栈：Kotlin + Jetpack Compose Material3 + Coroutines + DataStore + Moshi + OkHttp
> 包名：com.ltt.gkd
> 编译/目标 SDK：34，最低 SDK：26，JDK 17

---

## 一、项目概述

小狐是一款基于 Android 无障碍服务的开屏/弹窗广告自动跳过工具。通过监听应用窗口变化，自动识别并点击"跳过""关闭"等按钮，无需 Root。

### 核心特性
- 无障碍服务实时监听窗口事件，毫秒级响应
- 三源规则体系：内置（随 APK）+ 本地（用户自建）+ 订阅（GitHub Gist 共享）
- OCR 兜底识别：控件树找不到文字时截图识别坐标
- 规则云端共享：上传/订阅/去重/使用量统计
- 跳过历史记录与 7 天趋势统计
- 应用白名单（不对指定应用执行跳过）
- GitHub Token AES-GCM 加密存储
- 深色模式适配

### 2.2 核心数据模型

**Rule（单条规则）**
```kotlin
data class Rule(
    val id: String,                  // 规则唯一 ID
    val name: String,                // 规则名称
    val packageName: String,         // 目标包名（空=通用兜底）
    val priority: Int = 50,          // 优先级（100开屏/80弹窗/60Banner）
    val matchTargets: List<MatchTarget>, // 匹配目标列表
    val action: SkipAction,          // 跳过动作
    val throttleMs: Long = 3000,     // 节流间隔
    val enabled: Boolean = true,     // 是否启用
    val source: RuleSource,          // 来源：LOCAL/SUBSCRIBED/BUILT_IN
    val author: String = "",         // 作者（上传规则用）
    val subscribers: Int = 0         // 订阅数（使用量）
)
```

**MatchTarget（匹配目标）**
- `type`: TEXT / ID / DESC / OCR
- `text`: 关键词或正则列表
- `ids`: viewId 列表（type=ID 时）
- `regex`: 是否正则
- `caseInsensitive`: 大小写不敏感

**SkipAction（跳过动作）**
- `type`: CLICK_NODE / GESTURE_TAP / GLOBAL_BACK / GLOBAL_HOME
- `targetText`: 点击目标的文字

### 2.3 规则引擎工作流

```
窗口事件 → WindowEventProcessor.onAccessibilityEvent()
    → 提取当前包名 + 根节点
    → RuleEngine.candidates(packageName)  // 按包名过滤候选规则
    → 逐条 RuleMatcher.match(node, target)
       → TEXT: 遍历节点 text/contentDescription
       → ID:   匹配 viewId
       → DESC: 仅 contentDescription
       → OCR:  截图 MLKit 识别
    → 命中 → 检查节流 throttleMs → ActionExecutor.execute()
       → CLICK_NODE: performAction(ACTION_CLICK)
       → GESTURE_TAP: dispatchGesture 坐标点击
       → GLOBAL_BACK: performGlobalAction(GLOBAL_ACTION_BACK)
    → 成功 → SkipHistoryStore.record() + SettingsStore.incrementTotalSkip()
```

## 三、关键模块详解

### 3.1 三源规则仓库（RuleRepository）

合并顺序：**BUILT_IN → LOCAL → SUBSCRIBED**（后者覆盖前者同 ID 规则）

- **内置规则**：`assets/rules/*.json`，只读，随 APK 发布。加载时过滤掉未安装应用的规则（`getInstalledPackages`）。
- **本地规则**：`filesDir/rules/local/manual_<id>.json`，用户自建。
- **订阅规则**：`filesDir/rules/subscribed/*.json`，从 Gist 拉取。

### 3.2 DataStore 单例约束

**坑点**：`preferencesDataStore` 委托必须定义在**文件顶层**，不能放在类内部。否则每次实例化类都会创建新的 dataStore 属性，导致 `IllegalStateException: multiple DataStores active for the same file`。

**正确写法**：
```kotlin
// 文件顶层（整个应用共享一个 DataStore）
private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")

class SettingsStore(private val context: Context) {
    val logEnabled: Flow<Boolean> = context.dataStore.data.map { ... }
}
```

### 3.3 跳过历史存储（SkipHistoryStore）

- 持久化格式：JSONL（每行一条 JSON）
- 文件路径：`filesDir/history/history.jsonl`
- 内存保留最近 1000 条，按时间倒序
- 提供 `dailyCounts7d()` 生成 7 天趋势数据
- 场景推断：priority 100=SPLASH、80=POPUP、60=BANNER、其余=OTHER

### 3.4 订阅（多源）与共享（Gist）

订阅功能分「消费侧（订阅别人的规则）」与「共享侧（上传自己的规则）」，两者都以 `RuleSet` JSON 为唯一格式。

**消费侧：多源订阅**
- **源模型**：`SubscriptionSource{id,name,url,type,enabled,lastSyncAt,lastRuleCount,lastError}`，`SourceType` 为 `GIST`/`URL`。多源列表存于 `SubscriptionStore`（DataStore，顶层委托 `name="subscriptions"`，单键存 JSON 数组）。
- **链接自动识别**：`SubscriptionUrls` 从链接中抽取 32 位十六进制串判定 Gist，否则按普通 URL 处理。因此**订阅者只需粘贴链接，无需 GitHub 账号/Token**（Gist 链接、Gist raw、GitHub Pages、jsDelivr、任意静态 JSON 均可）。
- **统一同步**：`SubscriptionSyncer` 是手动同步与自动更新共用的取数逻辑——
  - GIST：`GistClient.fetchRuleSets(gistId)` 拉多份规则文件，并被动读取该 Gist 的 `comments` 数作为"订阅数/使用量"（只读、免鉴权）。
  - URL：HTTP GET，body 解析为一份 `RuleSet`。
  - 落地：写入 `subscribed/` 目录，文件名加 `<sourceId>__` 前缀；删除某源时按前缀清理，互不干扰。
  - 编排：`syncAndPersist`（单源）/`syncAll`（多源）负责回写 `SubscriptionStore` 同步元信息并 `repo.reload()` 一次。
- **自动更新**：`SubscriptionUpdateWorker`（WorkManager 周期任务，约束=有网络）遍历已启用源同步；`SubscriptionScheduler.reschedule()` 依据 `subscriptionEnabled`+`subscriptionIntervalHours` 排程/取消（`MainActivity` 用 `LaunchedEffect` 观察两个 Flow 触发）。**此前从未被启动的 `RuleSubscriptionService` 前台服务已删除**，改由 WorkManager 承担（更省电、无常驻通知、符合 Android 12+ 限制）。
- **共享仓库单例**：`RuleRepository` 收敛为 `App.repo` 全局唯一实例，界面/无障碍服务/Worker 共用；后台同步写入的新规则 `reload()` 后对运行中的服务即时可见。

**共享侧：GistClient（作者上传）**
- `uploadRuleSet()`：上传规则集到 Gist（需 Token）；`checkRuleExists(gistId,ruleId)`：上传前去重。
- `fetchSubscriberCount(gistId)`：读取 Gist 的 `comments` 数近似订阅数（只读）。
- `subscribe(gistId,token)`：向 Gist 评论一次以计数（需鉴权，**当前未接入**——按约定"不做需要订阅者配 GitHub 的计数"，使用量对 URL 源为 0、对 Gist 源为被动读取的评论数）。
- **去重机制**：上传时同 ID 规则已存在且作者不同 → 提示"只保留第一个创建者的版本"；作者是自己 → 允许覆盖；不存在 → 正常上传。

### 3.5 Token 加密（TokenCipher）

- 算法：AES-GCM（Android Keystore）
- IV + 密文 Base64 编码后存入 DataStore
- 读取时自动解密，不进入日志

### 4.4 规则使用量展示（使用量 = Gist 订阅数）

**数据来源（简单模型，无社区后端）**：使用量完全来自订阅量。Gist 上只承载两样东西——**作者**与**订阅数**；`GistClient.fetchSubscriberCount()` 以 Gist 的 `comments` 数近似订阅数（订阅者评论 "subscribed" 计数）。这是**订阅源级别的单一数字**：手动同步（`syncSubscribed`）会把该值统一赋给这个源的每一条规则。因此前端展示时按"源级订阅数"处理，**不做逐条累加**，也没有独立的社区服务或每条规则单独计数。

- **排序**：`RuleRepository` 加载订阅规则时按 `subscribers` 倒序。
- **汇总头**：订阅 Tab 顶部显示 `共 N 条 · 使用量（订阅数）X`，其中 `X = subscribed.maxOfOrNull { it.subscribers } ?: 0`（源级订阅数，非 `sumOf`；空列表安全）。
- **卡片元信息**：`RuleCard` 的 `showUsage=true` 时，在包名/优先级行下方追加一行——`Person` 图标 + 作者（空则显示"匿名"）、`Whatshot` 图标 + `使用 {formatCount(subscribers)}`。
- **热门徽章**：`subscribers >= HOT_SUBSCRIBER_THRESHOLD`（10）时，在来源徽章前展示琥珀色 `HotBadge`（火焰图标 + "热门"，深色模式自动切换暗色变体）。
- **数字格式**：`formatCount` 将 `>=10000` 显示为 `X.Y万`、`>=1000` 显示为 `X.Yk`、其余原样，整数时省略小数。
- **作用范围**：仅订阅 Tab 传 `showUsage=true`；本地/内置 Tab 不受影响。

#### 4.4.1 本地"已分享"标记与使用量联动

为让"上传分享"有可见正反馈（让用户觉得上传是件特别有意义的事），本地规则被作者上传后会显示特殊标记，并与订阅使用量联动：

- **数据**：`Rule` 新增 `uploaded: Boolean` 标记。`uploadRule` 成功后以 `uploaded=true` 回写本地副本；**发布到 Gist 的副本强制 `uploaded=false`**，避免其他订阅者在自己界面误看到"已分享"标记。
- **编辑保留**：`RuleEditScreen.buildCurrent()` 通过 `.copy(author/subscribers/uploaded)` 保留这三个字段，编辑并保存已分享规则不会丢失标记。
- **展示**：本地 Tab 中 `uploaded=true` 的规则，标题行显示蓝色星标 `已分享` 徽章（`UploadedBadge`），并在下方追加使用量行——同步到使用量后显示 `已被 N 人使用 · 感谢分享`（蓝色强调），未同步时提示 `已分享，同步后显示使用量`，同步到但为 0 时显示 `已分享，暂无使用量`。
- **联动来源**：`RulesScreen` 用 `subscribedUsageById`（订阅规则 `id → subscribers` 映射）为已分享本地规则取回使用量；该数值即作者自己 Gist 的订阅数（有多少人订阅/评论了该源），使用量**只来源于订阅同步**，本地不单独计数。

### 4.5 内置规则合集与整组选择

内置规则按"合集"组织，用户既能选单条规则、也能一键选整个合集：

- **合集组织**：一个 `assets/rules/*.json`（一个 `RuleSet`）即一个合集。已重写为覆盖市面常用/热门应用的 12 个合集 + `general.json` 通用兜底，共约 112 条规则；每条 `id = <packageName>_<scene>`（`_splash` 开屏 priority=100 / `_popup` 弹窗 priority=80），保证**全局唯一且 ID 与包名一致**（修复了此前的重复 ID、ID 与包名错配、损坏 ID 等问题）。合集示例：社交通讯、社区论坛、视频直播、音乐、电商购物、生活出行、新闻资讯、阅读听书、浏览器搜索、游戏、办公网盘、系统工具。
- **数据**：`RuleRepository` 新增 `builtInGroups: StateFlow<List<RuleGroup>>`，`RuleGroup(name, fileName, rules)`；在 `reload()` 中按合集分组，且每组仅保留已安装应用（或通用兜底）的规则，空合集自动隐藏。
- **批量开关**：`SettingsStore.setRulesEnabled(ids, enabled)` 在一次 DataStore 编辑内批量增删禁用集合，支撑"整组启用/禁用"。
- **UI**：内置 Tab 按合集分组——合集头部显示名称 + `已启用 X / N 条` + 原文预览按钮 + **整组 Switch**（全部启用时选中，切换即批量启用/禁用该合集所有规则）；头部下方是该合集每条规则的卡片，各带**单条 Switch**。

## 五、错误解决记录

### 5.1 DataStore 多实例崩溃
**现象**：应用启动即闪退
**错误**：`IllegalStateException: There are multiple DataStores active for the same file`
**根因**：`dataStore` 属性定义在 `SettingsStore` 类内部，`Logger.init` 又创建了第二个 `SettingsStore` 实例，导致同一文件被两个 DataStore 操作。
**解决**：将 `dataStore` 移到文件顶层；`Logger.init` 复用 `App.get().settings` 单例。

### 5.2 Toast 在非主线程崩溃
**现象**：点击订阅同步按钮后闪退
**错误**：`NullPointerException: Can't toast on a thread that has not called Looper.prepare()`
**根因**：`launchSafe` 使用 `Dispatchers.Default`，`Toast.makeText` 必须在主线程。
**解决**：`MainActivity.toast()` 用 `runOnUiThread` 包裹；`RuleEditActivity` 中用 `withContext(Dispatchers.Main)`。

### 5.3 OPPO 读取应用列表失败
**现象**：OPPO 手机上应用列表为空，打不开软件
**根因**：Android 11+ 需显式声明 `QUERY_ALL_PACKAGES` 权限。
**解决**：AndroidManifest 添加 `<uses-permission android:name="android.permission.QUERY_ALL_PACKAGES" />`，并提示用户在系统设置中手动授权。

### 5.4 闪退后无障碍服务误显示关闭
**现象**：应用崩溃后，首页显示服务"已关闭"，但系统设置中开关仍开着。
**根因**：之前仅用 `SkipAccessibilityService.instance != null` 检测，崩溃后进程死亡导致 instance 为 null。
**解决**：新增 `isAccessibilityEnabled()` 同时检查服务实例 + `AccessibilityManager.getEnabledAccessibilityServiceList` 系统设置状态。

### 5.5 Gradle 缓存损坏
**现象**：`assembleRelease` 报 `Could not read workspace metadata`
**根因**：清理 C 盘时删除了 `.gradle/caches`。
**解决**：删除整个 `.gradle/caches` 目录，重新构建（会重新下载依赖）。

### 5.6 订阅 URL 输入框光标跳到开头
**现象**：在设置页填写订阅 URL 时，输入一个字符后光标强制跳到文本最前面，无法正常输入。
**根因**：`OutlinedTextField` 的 `value` 直接绑定 `collectAsState` 的 Flow 值。用户输入时 `onValueChange` 异步写入 DataStore，Flow 重新发射后 `collectAsState` 更新 `value`，导致 TextField 内部状态重置、光标跳到开头。
**解决**：改用本地 `mutableStateOf` 作为输入唯一数据源，`onValueChange` 立即更新本地状态 + 异步存 DataStore；DataStore Flow 仅用于 `LaunchedEffect(Unit)` 初始化加载和外部变更同步。四个输入框（订阅 URL、更新间隔、Token、Gist ID）全部修复。

### 5.7 同步按钮无反馈
**现象**：规则页点击同步按钮后无任何反馈，用户不知道是否在执行。
**根因**：`syncSubscribed` 没有 loading 状态，也没有"同步中"提示。
**解决**：
- RulesScreen FAB 添加 `syncing` 状态，同步中显示 `CircularProgressIndicator` 替代图标
- `onSyncSubscribed` 签名改为 `((Boolean) -> Unit) -> Unit`，同步完成回调解除 loading
- 同步开始 Toast "正在同步订阅规则…"，成功/失败分别提示
- 无订阅源（Gist ID 为空）时自动跳转设置 Tab，订阅卡片自动展开并显示蓝色引导横幅

### 5.8 无障碍服务崩溃后停止
**现象**：应用崩溃后无障碍服务停止，跳广告失效。
**根因**：未处理的异常导致进程崩溃，系统停止无障碍服务。
**解决**：
- `App.setupCrashHandler()` 设置全局 `UncaughtExceptionHandler`：非主线程异常记录日志后吞掉，避免进程崩溃；主线程异常仍交系统默认处理器（避免 ANR）
- `onServiceConnected` 的组件装配抽成 `initComponents()` 并整体包 `runCatching`：任一组件初始化失败（如设备不支持 OCR）时仅记日志，不让异常冒泡停掉服务；失败时 `processor` 保持未初始化，`onAccessibilityEvent` 因 `::processor.isInitialized` 为 false 而安全忽略事件
- `onAccessibilityEvent` 中对 `processor.handle(event)` 包 `runCatching`，单个异常窗口事件就地兜底记 warn，不影响后续事件
- `onUnbind()` 崩溃恢复修正：
  - **Bug**：原实现里局部 `val intent` 遮蔽了 `onUnbind(intent)` 参数，导致 `super.onUnbind(intent)` 传入的是启动 Intent 而非原始参数；已重命名为 `launchIntent`
  - **Bug**：原实现在每次解绑都 `startActivity` 唤起主界面，用户在系统设置里主动关闭服务时会被强行弹回应用；现改为仅当 `isServiceStillEnabledInSettings()`（读取 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 是否仍含本应用组件）为 true——即"异常断开而非主动关闭"——才尝试唤起进程，配合系统对已启用无障碍服务的自动重启机制恢复

### 5.9 订阅功能半成品与双轨不一致
**现象**：订阅是半成品——手动同步走 `gistId` + Gist API，而"自动更新"的 `RuleSubscriptionService` 走 `subscriptionUrl` + 原始 HTTP，且**全代码没有任何地方 `startService` 启动它**（Manifest 声明了却是死代码）；`GistClient.subscribe()` 也从未被调用，订阅数永远不涨。
**根因**：并存两套语义重叠的字段（`gistId` 与 `subscriptionUrl`）+ 两条互不相通的取数路径 + 一个从未启动的前台服务。
**解决**（统一为多源订阅架构，详见 §3.4）：
- 新增 `SubscriptionSource`/`SubscriptionStore`/`SubscriptionUrls`/`SubscriptionSyncer`：一个源=一个链接，自动识别 Gist / 普通 URL，订阅者零 GitHub 配置。
- 自动更新改用 **WorkManager**：`SubscriptionUpdateWorker` 周期同步所有启用源，`SubscriptionScheduler.reschedule()` 由"自动更新开关+间隔"驱动排程/取消；**删除**从未启动的 `RuleSubscriptionService` 及其 Manifest 声明。
- `RuleRepository` 收敛为 `App.repo` 全局单例，界面/无障碍服务/Worker 共用，后台同步 `reload()` 后运行中的服务即时可见新规则。
- 订阅源管理 UI 落在「规则 → 订阅」Tab：源列表（启用开关/单源同步/删除/全部同步）+ 添加源对话框；设置页仅保留"自动更新开关 + 间隔 + 上传 Token/Gist"。

### 5.10 真机联调发现的两个无障碍配置 Bug（哔哩哔哩规则验证）
**环境**：OnePlus PJD110 / Android 16，冷启动哔哩哔哩抓取 `LTT_GKD` 日志。

**Bug 1：`packageNames=""` 导致服务收不到任何事件**
- **现象**：服务在"已启用"列表里、进程也在，但冷启动任意应用都零日志；`dumpsys accessibility` 显示 `Binding services:{}`（未真正绑定）。
- **根因**：`accessibility_service_config.xml` 里写了 `android:packageNames=""`，被系统理解为"只监听包名为空串的应用"，等于收不到真实事件。
- **解决**：删除该属性——省略即表示监听所有包，过滤交给代码里的白名单 + 候选规则。修复后 `dumpsys` 显示服务进入 `Bound services`。

**Bug 2：缺 `canTakeScreenshot` 导致 OCR 兜底抛 SecurityException**
- **现象**：日志 `处理无障碍事件异常` + `java.lang.SecurityException: Services don't have the capability of taking the screenshot.`，栈顶 `OcrManager.captureScreen`。
- **根因**：配置未声明 `android:canTakeScreenshot="true"`，`AccessibilityService.takeScreenshot()` 无权限。
- **解决**：加上 `android:canTakeScreenshot="true"`（API 30+，低版本忽略）。§5.8 的 per-event `runCatching` 正确把该异常兜成 warn 而非崩溃。

**验证结果**：两处修复后，冷启动哔哩哔哩稳定输出 `命中规则 tv.danmaku.bili_splash (哔哩哔哩开屏)` + `动作 CLICK_NODE -> true`（连续两次复现）。

**踩坑提示**：`adb install -r` 覆盖安装后无障碍服务绑定会失效，需用 `settings put secure enabled_accessibility_services` 关-开切换（或系统设置里手动重开）才能重新绑定。

### 5.11 "处理无障碍事件异常"突发 = 协程取消被误记（已修复）
**现象**：真机测试时偶发大量 `处理无障碍事件异常` 警告在同一毫秒从多个线程涌出。
**真实堆栈**（复现抓取）：
```
W LTT_GKD : 处理无障碍事件异常
W LTT_GKD : kotlinx.coroutines.JobCancellationException: Job was cancelled; job=SupervisorJobImpl{Cancelling}
I LTT_GKD : 无障碍服务已连接，规则就绪   ← 紧接着服务重连
```
**根因**：这些突发发生在**无障碍服务重绑**时（测试中反复切换 `enabled_accessibility_services` 会触发）。`onUnbind` 里的 `scope.cancel()` 取消了所有在途的 per-event 协程，每个协程抛 `JobCancellationException`，而 §5.8 加的 per-event `runCatching` 把这种**良性取消**当成错误记成了 `处理无障碍事件异常`，于是刷屏。**并非 OCR 截图刷屏**——`OcrManager` 本就有 1.5s 全局节流，且截图能力已在 §5.10 修好。（此前一版把它误判为 OCR 逐事件截图，特此更正。）
**修复（已实施）**：
- `onAccessibilityEvent` 不再把 `CancellationException` 当错误：单独捕获并**向上重抛**，保证结构化并发的取消语义不被吞掉、也不再误记 warn。
- **同步快照事件字段**：在回调里同步取出 `event.packageName/className` 再传入协程，避免异步使用已被系统回收/复用的 `AccessibilityEvent`（这是另一个潜在坑，`WindowEventProcessor.handle` 改为接收 pkg/cls 快照）。
- **OCR 节流加固**：由单一全局计时器改为**按包名节流 + in-flight 去重**，一次 OCR 未结束时不再发起新的 `takeScreenshot`，杜绝重叠截图。
**真机复验**：事件在途时切换无障碍服务（触发 `scope.cancel`），`处理无障碍事件异常` 与 `JobCancellation` 均为 **0 条**（修复前会刷屏），服务正常重连；12306 仍端到端命中（`命中规则 universal_popup_close` + `动作 CLICK_NODE -> true`），证明 pkg/cls 快照重构无回归。本轮哔哩哔哩/淘宝因开屏广告频次耗尽未能再刷出，但其命中已在 §八 前一轮验证。

### 5.12 进入首页无限跳转系统无障碍设置（服务点击自身界面）
**现象**：点进小狐首页后不停跳转到系统「无障碍设置」页，按返回回到首页后又立刻跳，形成死循环。
**诊断**：查跳过记录 `files/history/history.jsonl`，发现大量 `packageName=""` 但 `appName="小狐"` 的记录，`matchedText` 为 `关闭服务` / `累计跳过` / `服务已开启，自动跳过广告中` / `跳过`——即无障碍服务在**处理并点击小狐自己的界面**。
**根因**：小狐**没有把自身包名 `com.ltt.gkd` 排除**在处理之外。首页电源按钮的 `contentDescription` 为「关闭服务」，被通用兜底规则 `universal_popup_close`（匹配「关闭」）命中 → `CLICK_NODE` 点击电源按钮 → 触发 `onToggleService` → 打开 `ACTION_ACCESSIBILITY_SETTINGS`；从设置页返回首页时窗口内容变化再次命中 → 无限循环。`universal_splash_skip`/`universal_ocr_splash` 也会去点「累计跳过」等含"跳过"的自身文案。
**解决**：`WindowEventProcessor.processEvent` 最前面增加自我短路——`if (pkg == service.packageName) return`，**永不处理本应用自身窗口**（在候选筛选、节点匹配、OCR 之前）。
**验证**：修复后点电源按钮→跳无障碍（手动点击属正常）→按返回首页→静置 5s / 切换三个 Tab 制造窗口变化，前台始终稳定停在 `MainActivity` 不再自动跳；`history.jsonl` 新增 **0 条**自点记录。
**附注**：此 Bug 也暴露出通用兜底规则（裸匹配"关闭/跳过"）在**其它应用的正常界面**上同样可能误点，属后续需要收敛的风险（如限定仅开屏窗口/加更多上下文约束）。

**结果**（20 个已安装目标应用中，本轮明确命中的）：

| 应用 | 包名 | 结果 | 命中方式 |
|------|------|------|----------|
| 哔哩哔哩 | tv.danmaku.bili | 命中并点击 | TEXT `tv.danmaku.bili_splash` → CLICK_NODE true（多次复现） |
| 铁路12306 | com.MobileTicket | 命中 | TEXT |
| 携程旅行 | ctrip.android.view | 命中并点击 | TEXT → CLICK_NODE true |
| 淘宝 | com.taobao.taobao | 命中并点击 | OCR `universal_ocr_splash` @ Point(669,62)（"跳过"非文本节点，靠 OCR） |
| 其余 16 个 | 微信/QQ/抖音/京东/拼多多/支付宝/美团/高德/网易云/夸克/QQ浏览器/百度/闲鱼/企业微信/腾讯会议/百度网盘 | 本轮未命中 | 多为当次冷启动未投放开屏广告 |

**关键结论与坑**：
- **冷启动 vs 热启动（用户实测踩坑）**：点击一个进程仍在后台的应用属**热启动**，系统直接回到上次界面、**不放开屏广告**，自然"没跳过"——这是预期行为、非 Bug。开屏广告只在**真·冷启动**（进程被杀 / `force-stop` / 当天首次启动）才出现，且**屏幕须点亮并解锁**（息屏/Doze 会抑制广告渲染）。故正确的手动测试姿势 = 先 `force-stop`（或从最近任务划掉）应用 → 亮屏 → 再打开。补充：开屏广告**按频次投放**，短时间内反复冷启动会不再出广告。
- **补充验证**：京东冷启动 3/3 命中（`com.jingdong.app.mall_splash` 开屏 + `_popup` 弹窗）、12306 冷启动 2/3 命中（`universal_popup_close`），动作均 `CLICK_NODE -> true`；携程本轮 0/3（此前已命中过，判为频次上限）。
- **开屏广告按频次投放**：单次冷启动经常没有广告，故 `NO-HIT` ≠ 规则失效；需多次冷启动、或结合控件树 dump / OCR 判断。哔哩哔哩前两次命中、批量轮次里又 NO-HIT 即为例证。
- **两条链路都已验证可用**：TEXT 匹配（哔哩哔哩/12306/携程/京东）与 OCR 兜底（淘宝）均真机命中。
- **订阅自动更新链路通**：日志出现 `订阅自动更新已排程：每 24 小时`，说明 WorkManager 调度按设置生效。
- **批量测试期间无 `SecurityException`**：§5.10 修复的 `canTakeScreenshot` 生效；20 应用批量跑未再出现截图权限异常。
- 发现的两处配置 Bug 见 §5.10（已修复）；`处理无障碍事件异常` 突发（协程取消被误记）见 §5.11（已修复）。
